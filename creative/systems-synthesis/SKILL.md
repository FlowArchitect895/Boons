# Systems synthesis

A system is a set of interacting parts whose relationships produce behavior:
a power system, story, sport, nervous system, business, learning process or
routine. Read the mechanism behind a reference, not its surface, and build
something new. The goal is not maximum complexity; it is a coherent system
whose behavior and limits can be explained.

## Ways in

- **Combine:** fuse functions of two or more systems.
- **Map across domains:** project a mechanism from one domain onto another.
- **Read the meta:** identify shared underlying structure in a genre or body of work.
- **Build from scratch:** design an original system for a stated purpose, tone and medium.

References provide high-level functions (pacing, constraint, feedback,
escalation, adaptation, resource pressure), not protected characters, named
abilities, scenes or text.

## Workflow

1. **Establish purpose and scale.** Identify purpose, participants, environment,
   medium and tone. Determine whether the user wants a concept, practical
   framework, game mechanic, narrative system or implementable specification.
   Ask when a missing choice materially changes design.
2. **Separate source from invention.** For each reference, distinguish
   **Observed** (directly present), **Interpreted** (mechanism inferred) and
   **Proposed** (new rule or relationship). Do not present inference as fact or
   proposal as source material.
3. **Find the organizing principle.** State the central idea briefly. Explain
   why the mechanisms belong together, what each contributes and what is
   excluded. Avoid superficial combinations that borrow only names or aesthetics.
4. **Define the anatomy.** Specify only necessary components: actors/entities,
   inputs/resources, starting conditions, state variables, rules/decisions/
   transitions, outputs, boundaries and failure states. Define key terms
   consistently. Refine any rule that cannot be applied.
5. **Map dependencies and feedback.** Show what depends on what and how
   changes propagate. Identify reinforcing/balancing loops, delays, bottlenecks
   and runaway behavior where relevant. Distinguish causal dependency from
   thematic association. Mark essential versus optional components.
6. **Make costs real.** Give advantages meaningful constraints. Consider time,
   energy, attention, resources, risk, opportunity cost, complexity,
   maintenance and access. Costs should affect choices, not merely decorate
   them. Add counterplay, recovery or ways to interrupt dominant strategies.
7. **Stress-test before polishing.** Test ordinary use; boundary conditions
   (minimum, maximum, scarce, empty or overloaded); interactions between
   components; exploits or dominant strategies; failure and recovery; and
   growth over time when state accumulates. Check contradictions, circular
   dependencies, infinite loops, unbounded combinations, inaccessible resources
   and runaway feedback. Use a worked example or small model when useful.
8. **Run an adversarial review.** Take the strongest plausible opposing view of
   the design. Identify the assumption most likely to fail, a benign or simpler
   explanation for an apparent effect, a case where the system produces the
   wrong outcome, and evidence that would change the design. Do not manufacture
   consensus: record unresolved trade-offs or competing interpretations.
9. **Revise for coherence and simplicity.** Correct contradictions. Remove
   components that add complexity without meaningful behavior. Prefer a small
   rule set with clear interactions over disconnected feature lists. State
   assumptions and what changes if they fail.
10. **Present in the requested form.** Explain the organizing idea, rules and
    interactions at the needed level. Use examples to demonstrate behavior.
    Mark unresolved choices instead of silently deciding them.

## Stop or narrow

If the request depends on reproducing recognizable protected characters,
signature abilities, scenes or text, decline that part and offer a distinct
design based on broad functional traits. Do not claim a proposal is canon
unless approved. If purpose or core constraints are too ambiguous, ask rather
than hide decisions inside assumptions.

## Verification

Check that observations, interpretations and inventions are distinguishable;
terms and rules are consistent; dependencies and feedback are understandable;
costs affect choices; ordinary use, edge cases and an adversarial case are
tested; contradictions, unbounded loops and dominant exploits are addressed;
complexity is justified; and references inform only high-level functions.
State unresolved uncertainties. A stress-tested proposal is not proof that a
real-world system will behave exactly as modeled.
